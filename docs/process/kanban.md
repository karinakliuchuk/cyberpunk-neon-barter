# Правила потоку задач (Канбан), ЛР №8

Команда: Ян (Analyst), Артем (Architect), Каріна (Integrator), Настя (QA / Docs).
Дошка: GitHub Projects, подання Board, групування за полем `Status`.

## 1. Стани задачі

| Стан | Що означає |
|---|---|
| **Todo** | Задачу визначено й описано, але виконання ще не розпочато. |
| **In Progress** | Виконавець розпочав роботу: створено гілку, є зміни в коді або документах. |
| **Review** | Виконавець створив запит на злиття (PR), автоматичні перевірки запущено, результат чекає перевірки іншим учасником. |
| **Done** | Інший учасник перевірив зміни, автоматичні перевірки пройшли, зміни об'єднано з `main`. |

## 2. Початок і завершення роботи

- **Початок.** Учасник бере картку з `Todo` лише тоді, коли в картці є опис очікуваного результату, артефакт (файл) і залежності від інших задач виконано, а ліміт незавершеної роботи (розділ 4) дозволяє почати нову задачу. Картки беруть за пріоритетом: спочатку ті, від яких залежать інші задачі.
- **Початок фіксується** переведенням картки в `In Progress` і записом часу в `docs/process/flow-events.csv`.
- **Завершення.** Картку переводять у `Done` лише після об'єднання PR з `main` та успішного запуску тестів. Незавершені й заблоковані задачі залишаються у своїх станах.

## 3. Умови переходу між станами

| Перехід | Умова |
|---|---|
| Todo → In Progress | Є вільне місце в межах ліміту; задача має опис результату; залежності виконано. |
| In Progress → Review | Створено PR із посиланням на картку; запущено `dotnet test`; опис PR містить, що змінено і як перевірено. |
| Review → In Progress | Перевіряльник залишив зауваження: виконавець повертає картку й усуває їх. Час першого початку роботи не скидається. |
| Review → Done | Перевіряльник підтвердив зміни, автоматичні перевірки зелені, PR об'єднано з `main`. |

## 4. Ліміт незавершеної роботи (WIP)

- У стані **In Progress** одночасно не більше **2 карток** на всю команду.
- Стан **Review** окремого ліміту не має, але картки на перевірці мають вищий пріоритет, ніж початок нової задачі: якщо ліміт у `In Progress` вичерпано або є картки в `Review`, учасник спершу допомагає з перевіркою.
- Заблоковані картки залишаються у своєму стані й **враховуються в ліміті**, щоб блокування не приховувало реальної незавершеної роботи.
- Ліміт є правилом команди: GitHub Projects не блокує перехід картки, тому перед початком нової задачі учасник сам перевіряє кількість карток у `In Progress`.

## 5. Дії в разі блокування

1. Учасник додає до картки позначку `blocked` і коментар: причина, час початку блокування, хто допоможе її усунути.
2. Блокування повідомляють команді в чаті.
3. Відповідальний за усунення перешкоди (учасник, від якого залежить задача, або Артем як Architect у технічних питаннях) відповідає в картці.
4. Після усунення перешкоди позначку знімають і додають у коментар час відновлення роботи.

Приклад: тест Яна не проходить, бо `AuthEndpoints.cs` ще не змінено Артемом. Картку позначають `blocked`, причина: залежність від задачі Артема, відповідальний: Артем.

## 6. Хто та як перевіряє результат

- Результат кожної картки перевіряє **інший учасник команди**, не виконавець.
- Перевіряльник дивиться: PR відповідає опису картки, `dotnet test` на PR зелений, зміни не містять сторонніх файлів, документація й RTM оновлені, якщо задача цього вимагає.
- За технічні зміни (код, міграції) остаточне підтвердження дає Артем, за документи й тести (процес, RTM) перевіряє Настя або Артем.
- Після підтвердження PR об'єднує перевіряльник або автор за домовленістю, картка переходить у `Done`.

## 7. Класи обслуговування

| Клас | Коли застосовується | Правило |
|---|---|---|
| Звичайний | Більшість задач | Береться за пріоритетом із дотриманням ліміту. |
| Терміновий | Дефект, що блокує роботу всієї команди | Береться раніше інших; одночасно не більше однієї термінової задачі. Перевірка результату не скасовується. |
