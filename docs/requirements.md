# Вимоги до системи Cyberpunk Neon Barter v1.0

Документ містить SRS-фрагмент версії v1.0: межі, функціональні та нефункціональні вимоги з критеріями приймання. Вимоги спираються на Product Vision і межі v1.0 з ЛР №1.

## 1. Межі v1.0

**Входить до v1.0:**

- збереження карток учасників з базовими контактами або позивним;
- створення оголошення обміну («віддаю» та «потребую») із фіксованого списку категорій;
- виявлення простого замкненого 3-стороннього циклу обміну;
- відображення деталей знайденого ланцюжка та кроків передачі;
- фіксація статусу виконання операції обміну.

**Свідомо відкладено:**

- автономний P2P/Mesh-обмін без сервера;
- довільний текстовий опис найменувань і фотографії;
- ланцюжки з 4 і більше учасників та частковий компенсаційний обмін;
- рейтинг надійності учасників і арбітраж;
- автоматичні SMS/Push-сповіщення.

## 2. Словник термінів

| Термін | Значення |
|---|---|
| Учасник | Особа із зареєстрованою карткою (позивний і контакт), яка бере участь в обміні |
| Оголошення обміну | Заявка учасника типу «віддаю» або «потребую» із категорією та кількістю |
| Категорія | Одне зі значень фіксованого списку: вода, їжа, ліки, зв'язок, енергія |
| Одиниця | Стандартизована одиниця («пакет») без дробових значень |
| Цикл обміну | Замкнений ланцюжок із 3 учасників: A → B → C → A |

## 3. Функціональні вимоги

| ID | Вимога | Критерій приймання |
|---|---|---|
| FR-01 | Система повинна дозволяти зареєструвати картку учасника з позивним і контактом. | **AC-01:** після передачі коректних даних картка збережена, учасник може створювати оголошення. |
| FR-02 | Система повинна дозволяти зареєстрованому учаснику створити оголошення обміну із типом («віддаю» або «потребую»), категорією зі списку та кількістю в цілих одиницях. | **AC-02:** якщо дані коректні, оголошення збережене зі статусом «Активне» і доступне для пошуку циклу; учасник бачить підтвердження. |
| FR-03 | Система повинна відхиляти оголошення, категорія якого не входить до фіксованого списку. | **AC-03:** оголошення із категорією поза списком не зберігається; учасник отримує повідомлення про недопустиму категорію. |
| FR-04 | Система повинна відхиляти оголошення, кількість якого не є цілим числом більшим за нуль. | **AC-04:** оголошення з кількістю 0, від'ємною або дробовою не зберігається; учасник отримує повідомлення про причину. |
| FR-05 | Система повинна відхиляти оголошення, у якому не заповнено обов'язкові поля або яке створює незареєстрований учасник. | **AC-05:** такі оголошення не зберігаються; повідомлення вказує, які поля відсутні або що учасника не знайдено. |
| FR-06 | Система повинна знаходити замкнений 3-сторонній цикл обміну між активними оголошеннями «віддаю» і «потребую». | **AC-06:** для набору, де A віддає те, що потребує B, B віддає те, що потребує C, а C віддає те, що потребує A, система повертає цей цикл. |
| FR-07 | Система повинна відображати деталі знайденого циклу: учасників, ресурси та кроки передачі. | **AC-07:** для знайденого циклу відображено трьох учасників і три кроки передачі «хто → кому → що». |
| FR-08 | Система повинна дозволяти зафіксувати й переглянути статус виконання операції обміну. | **AC-08:** після зміни статусу нове значення зберігається і відображається в деталях циклу. |

## 4. Нефункціональні вимоги

| ID | Характеристика | Вимога | Критерій приймання |
|---|---|---|---|
| NFR-01 | Продуктивність | Створення оголошення повинно завершуватися швидко. | **AC-09:** відповідь на коректне створення оголошення з'являється не пізніше ніж за 1 с у 95 % запитів у навчальному середовищі (до 1000 активних оголошень). |
| NFR-02 | Продуктивність | Пошук 3-стороннього циклу не повинен деградувати зі збільшенням бази. | **AC-10:** на наборі з 1000 активних оголошень пошук завершується не пізніше ніж за 5 с. |
| NFR-03 | Коректність | Знайдені цикли повинні бути валідними. | **AC-11:** на тестовому наборі з не менш ніж 20 сценаріїв алгоритм знаходить усі очікувані цикли і не повертає жодного хибного. |
| NFR-04 | Цілісність даних | Відхилене оголошення не повинно змінювати дані системи. | **AC-12:** після будь-якої відмови за FR-03…FR-05 кількість оголошень у системі не змінюється. |
| NFR-05 | Зрозумілість помилок | Кожна відмова повинна містити причину. | **AC-13:** кожна відповідь про відмову містить код помилки та текстову причину. |
