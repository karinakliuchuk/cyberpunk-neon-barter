## 2. Опис

Користувач, який має активні оголошення типу «віддаю» та «потребую», ініціює пошук замкненого 3-стороннього циклу обміну (A → B → C → A). Система будує граф відповідностей між активними оголошеннями різних користувачів, знаходить валідні цикли, у яких кожен учасник віддає те, що потребує наступний, та обирає один цикл за детермінованим правилом. Після цього система резервує обрані оголошення та створює `BarterDeal` зі статусом `PendingConfirmations`, після чого передає керування до UC-03 «Підтвердити участь у бартерній угоді».

## 3. Передумови (Preconditions)

- Користувач **авторизований** у системі.
- Користувач має **картку учасника** (FR-01).
- У користувача є щонайменше одне активне оголошення типу «віддаю» та щонайменше одне активне оголошення типу «потребую» (FR-02).
- У системі існують активні оголошення інших користувачів, які потенційно можуть утворити цикл.
- Категорії оголошень належать фіксованому списку (вода, їжа, ліки, зв'язок, енергія), кількості — цілі числа > 0 (FR-03, FR-04).

## 4. Післяумови (Postconditions)

**Успішний сценарій:**

- Знайдено валідний цикл A → B → C → A з трьох різних користувачів.
- Обрані оголошення переведено в статус `Reserved`.
- Створено `BarterDeal` зі статусом `PendingConfirmations`.
- Створено записи `BarterParticipant` для трьох учасників з `IsConfirmed = false`.
- Встановлено `ExpiresAt` для очікування підтверджень.
- Відображено деталі ланцюжка: учасники, ресурси, кроки передачі (FR-07).
- Подію зафіксовано в `AuditLog`.

**Неуспішний сценарій (немає циклу / немає власних оголошень / оголошення втратили активність):**

- `BarterDeal` не створюється.
- Статуси оголошень не змінюються.
- Користувач отримує повідомлення з кодом помилки та текстовою причиною (NFR-05).
- Подію зафіксовано в `AuditLog`.

## 5. Основний потік (Main Flow)

| # | Актор | Дія |
|---|---|---|
| 1 | Користувач | Обирає свої активні оголошення типу «віддаю» і «потребую» |
| 2 | Система | Перевіряє, що в користувача є активні оголошення обох типів |
| 3 | Користувач | Запускає пошук циклу |
| 4 | Система | Будує граф відповідностей: ребро X→Y існує, якщо пропозиція X задовольняє потребу Y (категорія і кількість) |
| 5 | Система | Шукає замкнений шлях A→B→C→A з трьох різних користувачів |
| 6 | Система | Перевіряє, що всі три користувачі різні |
| 7 | Система | Перевіряє відповідність: потреба A ↔ пропозиція B, потреба B ↔ пропозиція C, потреба C ↔ пропозиція A; кількості — цілі й рівні |
| 8 | Система | Якщо валідних циклів кілька — обирає один за детермінованим правилом (порядок за ID учасників) |
| 9 | Система | Перевіряє, що всі три обрані оголошення ще активні |
| 10 | Система | Резервує оголошення: статус `Reserved` |
| 11 | Система | Створює `BarterDeal` зі статусом `PendingConfirmations` та `BarterParticipant` для трьох учасників |
| 12 | Система | Відображає деталі ланцюжка та кроки передачі «хто → кому → що» |
| 13 | Система | Логує подію в `AuditLog` |
| 14 | Система | Передає керування до UC-03 (очікування підтверджень) |

## 7. Виключні ситуації (Exceptions)

| ID | Ситуація | Реакція системи |
|---|---|---|
| E1 | Користувач не авторизований | Повернути `401 Unauthorized`, перенаправити на вхід |
| E2 | Користувач не має картки учасника | Повернути `403 Forbidden` з поясненням |
| E3 | Перевищено ліміт часу пошуку (NFR-02) | Перервати пошук, повернути `504 Gateway Timeout` або частковий результат |
| E4 | Помилка збереження в БД при резервуванні/створенні угоди | Відкат транзакції, `500 Internal Server Error`, логування |
| E5 | Конкурентний доступ: оголошення зарезервовано іншим процесом | Повернутися до пошуку (A5), за потреби — `409 Conflict` |

## 8. Критерії приймання (Acceptance Criteria)

- **AC-02.1 (FR-06):** Для набору, де A віддає те, що потребує B, B віддає те, що потребує C, а C віддає те, що потребує A, система повертає цей цикл.
- **AC-02.2 (FR-06, NFR-03):** Цикл складається з трьох **різних** користувачів; повторення учасника не допускається.
- **AC-02.3 (FR-06):** Відповідність перевіряється за схемою «потреба A ↔ пропозиція B», «потреба B ↔ пропозиція C», «потреба C ↔ пропозиція A»; кількості — цілі й рівні.
- **AC-02.4 (FR-07):** Для знайденого циклу відображено трьох учасників і три кроки передачі «хто → кому → що».
- **AC-02.5 (FR-08):** Обрані оголошення переведено в статус `Reserved`; створено `BarterDeal` зі статусом `PendingConfirmations`.
- **AC-02.6 (NFR-02):** На наборі з 1000 активних оголошень пошук завершується не пізніше ніж за 5 с.
- **AC-02.7 (NFR-03):** На тестовому наборі з не менш ніж 20 сценаріїв алгоритм знаходить усі очікувані цикли і не повертає жодного хибного.
- **AC-02.8 (NFR-05):** Кожна відмова (A1, A2, A5) містить код помилки та текстову причину.
